# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local website that tracks a Valorant 5-stack through the unofficial HenrikDev API, keeps per-player stats for games where all five members were on the same team, and generates sportsbook-style odds that the squad bets on with virtual credits. `README.md` covers the user-facing behaviour and every `config.json` key.

**Hard constraint:** Python 3.10+ standard library only, with no third-party packages. The frontend (`web/`) is plain JS/CSS/HTML with no build step and no dependencies. Keep it that way.

## Commands

```
python server.py                  # run (needs config.json; created from config.example.json on first run)
python server.py --demo           # synthetic data in data/demo.db, never calls the API
python server.py --no-browser --port=8090 --no-tunnel --config=other.json
python server.py --tunnel         # also publish via Cloudflare quick tunnel (requires site_password)
python tests/selftest.py          # the only test suite: offline, end-to-end, prints "selftest OK"
```

Don't pipe `tests/selftest.py` into `head`: the closed pipe makes the tracker's `print` raise `OSError` on Windows. Redirect to a file instead.

There is no linter config, no test framework and no single-test runner. `tests/selftest.py` is one `main()` of sequential asserts against a `FakeClient` that stands in for `HenrikClient`. Add new checks there, and extend `FakeClient` when new API calls are involved. `HENRIK_API_KEY` in the environment overrides `api_key` from the config.

## Architecture

The data flows one way: **HenrikDev → tracker → SQLite → stats/odds → JSON API → SPA**, and bets feed back in at settlement.

All backend code lives in the `fivestack/` package and imports its siblings relatively (`from .db import DB`). The root `server.py` is only a launcher for `fivestack.app.main`. `fivestack/config.py` defines `ROOT` as the repository root, and `web/`, `data/`, `tools/` and `config.json` are resolved from it, so they stay at the top level.

- `fivestack/app.py` wires everything together. `fivestack/config.py` loads and validates `config.json`, and `fivestack/auth.py` holds the password and bettor-session cookie logic. `App` owns one instance each of `DB`, `OddsEngine`, `BetManager`, `Auth`, `Tunnel`, and (only when the config is valid and not in demo mode) `HenrikClient` + `Tracker`. `Handler` is a stdlib `BaseHTTPRequestHandler` that routes by hand in `do_GET`/`_api_get`/`do_POST`/`do_DELETE`. New endpoints go there. Every route except `/login`, `/logout` and `/style.css` sits behind the cookie check when `site_password` is set. `/api/bettors/reset` also checks the `X-Admin-Password` header.
- `tracker.py` is the 5-stack detection (the module docstring explains the algorithm). Each sync fetches every member's *stored matches* (one API call per member). A match id seen for all members on the same team counts as a game. A match missing exactly one member is checked against the v4 match-details endpoint. Everything else goes into the `rejected_matches` meta key and is never re-checked. Polling runs on a daemon thread (`start()`/`_loop`), and `/api/sync` triggers `request_sync()` on another thread. When a sync records new matches, it calls the `on_new_matches` callback, which is where bets get settled.
- `henrik.py` is a thin urllib client with a global minimum request interval, rate-limit header tracking and automatic 429 backoff. Stay inside the budget of about 30 requests per minute (`details_per_sync` caps enrichment fetches).
- `db.py`: one shared `sqlite3` connection (`check_same_thread=False`, WAL) guarded by an `RLock`. The poller thread and the request threads all go through it. Multi-step writes (balance adjustment + bet insert/update) wrap `with db.lock:`. The schema is `CREATE TABLE IF NOT EXISTS` only, with no migrations, so a column added to an existing table won't reach an existing `data/tracker.db` unless you add migration logic. The `meta` table is a JSON key/value store (`cookie_secret`, `rejected_matches`, `last_sync`, `backfilled`, `history_backfilled`).
- `member_games` holds each member's own line from every stored match in a counted mode, 5-stack or not. `db.baseline_rows()` returns the rows whose `match_id` is not in `matches` (the member's non-5-stack games). Sync always inserts these rows with `INSERT OR IGNORE`, and `history_backfilled` forces one full fetch on databases that predate the table.
- `stats.py`: pure aggregation over DB rows. `deviation()` compares a member's 5-stack rows with their baseline rows (pooled values plus a two-sample z statistic → verdicts shown on the Players page). `player_metrics()` defines the per-game stat values (ACS, ADR, HS%, and so on), and both `stats.py` and bet settlement use it, so a change there alters both the displayed stats and settlement results.
- `insights.py`: `build_insights(db)` shapes every dataset for the Visualizations tab (`/api/insights`): chronological games with session number, rolling form, damage share and role-comp key; close/blowout/momentum records; per-player map, win-vs-loss and aim splits; bettor profit series. Keep aggregation here, where the self-test covers it. The only thing binned in the browser is the day × time-of-day heatmap, because it needs the viewer's local time zone. `ROLES` maps agents to roles, so add new agents there.
- `rewards.py`: `RewardManager.pay_for_match()` runs from `App.on_new_matches` after bet settlement. For every game it pays each member `game_reward` (plus optional `win_reward` for a win) and a performance bonus of up to `performance_bonus_max`. The bonus is the share of the member's own earlier 5-stack games (`db.player_rows()` from before this match, not the non-5-stack baseline) that this game's ACS beats, and it is half the maximum when there are fewer than 5 baseline games. It is rounded to the nearest `BONUS_STEP` (5). Rewards go to the bettor account named by `members[].bettor` in config.json, else by the nickname's entry in the committed `bettor_names.json` (loaded by `config.load_bettor_names()`), else the nickname itself. The account is created unclaimed if missing. The `rewards` table has one row per member per game, so re-syncs never pay twice. `db.pay_reward` records the row and credits the balance in one transaction. Games that started before meta `rewards_since` never pay. Leaderboard profit and ROI subtract rewards, so they stay betting-only, and `reset_betting` clears rewards.
- `gamestate.py`: `ending(match)` reads how a game ended from its score: complete (a team reached the mode's rounds-to-win target), forfeit (a surrender: stopped short after more than 4 rounds), or no contest (a remake within the first 4 rounds). The tracker never records no-contest games, and keeps them out of `member_games`. Forfeits are recorded, and v4 `teams[].won` overrides the score for the result. `bets._evaluate` settles a forfeit's non-match-result markets only if they were already decided (an over on a counting stat already past the line), and voids the rest. Parlays get this for free, because `_evaluate_parlay` runs each leg through `_evaluate`, so a surrender-voided leg is dropped like any void leg. `odds.py` scales a forfeit's counting stats to `full_game_rounds()` and weights it by the share of a game played. The total-rounds market excludes forfeits.
- `odds.py`: `OddsEngine.build(db, context)` recomputes the whole odds board on each call. It is stateless and uses recency-weighted samples, boosted by the chosen map/agent in `context`. Market ids are strings: `ou:<stat>:<puuid>`, `top:<stat>`, `team:win`, `team:rounds`. `find_market()` looks them up.
- `bets.py`: `place()` rebuilds the board with the bettor's context and locks in the current odds and line on the bet row. `place_parlay()` does the same for 2-10 legs (each from a different market): it stores the legs as a JSON list in the bet's `context` column with `market_type="parlay"`, and the bet's own `odds_decimal` is the product of the legs' decimal odds. `settle_for_match()` settles every pending bet whose `placed_ts` is before the match's `started_ts`, whatever the map; a parlay is settled leg by leg through `_evaluate_parlay()` (reusing `_evaluate()` per leg), which writes each leg's result back into `context` for the UI. Void results (landing exactly on the line, ties, draws) refund the stake; a void leg inside a parlay is just dropped from the payout math instead, and the whole parlay only voids if every leg does.
- `tunnel.py` downloads `cloudflared` into `tools/` and runs it as a child process. It refuses to start without `site_password`.
- `web/app.js`: a single IIFE SPA with views `overview/players/viz/odds/bettors/matches/setup`, a global `state` object, and an `api()` fetch helper. It remembers the bettor name, odds format and stake in `localStorage`. On the Odds & Bets tab, `betsSection()` groups pending/settled bets by bettor into ticket-styled "slip" cards (`bettorSlips()`/`betTicket()`) instead of one flat table, and a parlay bet's legs (parsed from its `context` JSON) render nested inside the ticket. The bet slip (`slipHtml()`) shows a Singles/Parlay toggle once 2+ picks are queued; in parlay mode it posts `{legs, stake, context}` to `/api/bets` instead of one request per pick.
- `web/viz.js` (`window.FiveViz`) draws the Visualizations tab as hand-built SVG/HTML charts. `html()` returns the cards with empty `[data-chart]` slots, and `mount()` draws each slot at its real pixel width and redraws on resize. Chart colors are CSS variables in `style.css` (`--s1…--s8` per player slot, plus `--div-*`, `--aim-*`, `--pair-*`, `--axis`), defined in all three theme blocks, so the theme toggle needs no redraw. Tooltip specs sit in `data-tip` JSON and are rendered with `textContent`. Every chart card also gets a "Show as table" view.

`config.json`, `data/` and `tools/` are gitignored. Delete `data/tracker.db` to rebuild history from scratch.
