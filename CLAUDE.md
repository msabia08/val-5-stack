# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is a copy of this file for other AI coding agents (such as Codex), identical except for its `# AGENTS.md` title. After changing this file, rebuild it with `{ echo "# AGENTS.md"; tail -n +2 CLAUDE.md; } > AGENTS.md`; CI fails if the two differ below the title.

## What this is

A local website that tracks a Valorant 5-stack through the unofficial HenrikDev API, keeps per-player stats for games where all five members were on the same team, and generates sportsbook-style odds that the squad bets on with virtual credits. `README.md` covers the user-facing behaviour and every `config.json` key.

**Hard constraint:** Python 3.10+ standard library only, with no third-party packages. The frontend (`web/`) is plain JS/CSS/HTML with no build step and no dependencies. Keep it that way.

## Commands

```
python server.py                  # run (needs config.json; created from config.example.json on first run)
python server.py --demo           # synthetic data in data/demo.db, never calls the API
python server.py --no-browser --port=8090 --no-tunnel --config=other.json
python server.py --tunnel         # also publish via Cloudflare quick tunnel (requires site_password)
python tests/selftest.py          # the only test suite: offline, end-to-end, prints "selftest OK" (CI runs it on 3.10 and 3.12)
```

Line endings are LF, enforced by `.gitattributes` (`.bat` files are CRLF); write new files with LF.

Keep the code runnable on Python 3.10 (the README's minimum; CI checks it): for example, no reusing an f-string's own quote character inside `{…}` (3.12+ only).

Don't pipe `tests/selftest.py` into `head`: the closed pipe makes the tracker's `print` raise `OSError` on Windows. Redirect to a file instead.

There is no linter config, no test framework and no single-test runner. `tests/selftest.py` is a series of named sections (`@section("forfeits")` functions) run in order against a `FakeClient` that stands in for `HenrikClient`; each prints `ok: <name>`, and a failure prints the traceback, then `FAIL: <name>`, and stops. The sections share one database and a `shared` namespace (bets placed in "bets" are settled in "settlement"), so they can't run on their own; anything a later section needs goes on `shared`. Add new checks to the matching section or a new one, and extend `FakeClient` when new API calls are involved. It also fails if a key in `config.example.json` is missing from the README's configuration table. `HENRIK_API_KEY` in the environment overrides `api_key` from the config.

## Branches and pull requests

Several people push to this repository (`msabia08/val-5-stack`), so every change goes through a pull request into `main`; never commit to `main` directly. AI agents commit, push and open pull requests only when asked.

1. `git fetch`, then branch off the latest `origin/main` with a short kebab-case name for the change (`forfeit-handling`, `scoreboard-counters`). Branches live in this repository, not in forks.
2. Before committing, run the self-test and `for f in web/*.js; do node --check "$f"; done`, and check anything visible in the browser with `python server.py --demo` (no console errors). Update `docs/DATA.md`, the README and this file (then rebuild `AGENTS.md`) as `.github/pull_request_template.md` lists.
3. Commit with a short imperative summary line and a body that says what changed and why.
4. `git push -u origin <branch>`, then `gh pr create --base main` with the template's Summary and a ticked Test plan.
5. CI (`.github/workflows/selftest.yml`) must pass: `gh pr checks <number> --watch`. Pull requests are merged with a merge commit ("Merge pull request #N"), not squashed.

If `main` moves while a branch is open, merge `origin/main` into the branch rather than rebasing, and never force-push a branch that's already pushed. Work that builds on an unmerged pull request branches from that pull request's branch, and its pull request targets that branch (`gh pr create --base <first-branch>`) so the diff shows only the new work. Merge the first one, then switch the second to `main` (`gh pr edit <number> --base main`; GitHub does this by itself if the first branch was deleted on merge).

## Architecture

`docs/DATA.md` is the data reference: HenrikDev response structures (captured from real responses with `scripts/inspect_henrik.py`), every database table, every `/api/*` endpoint, and API data we don't use yet. Check it before assuming a field exists, and update it when you add a table, column or endpoint.

The data flows one way: **HenrikDev → tracker → SQLite → stats/odds → JSON API → SPA**, and bets feed back in at settlement.

All backend code lives in the `fivestack/` package and imports its siblings relatively (`from .db import DB`). The root `server.py` is only a launcher for `fivestack.app.main`. `fivestack/config.py` defines `ROOT` as the repository root, and `web/`, `data/`, `tools/` and `config.json` are resolved from it, so they stay at the top level.

- `fivestack/app.py` wires everything together. `fivestack/config.py` loads and validates `config.json`, and `fivestack/auth.py` holds the password and bettor-session cookie logic. `App` owns one instance each of `DB`, `OddsEngine`, `BetManager`, `Auth`, `Tunnel`, and (only when the config is valid and not in demo mode) `HenrikClient` + `Tracker`. `Handler` is a stdlib `BaseHTTPRequestHandler` that routes by hand in `do_GET`/`_api_get`/`do_POST`/`do_DELETE`. New endpoints go there. Every route except `/login`, `/logout`, `/style.css` and `/assets/*` (images, which the login page shows too) sits behind the cookie check when `site_password` is set. `_static()` serves `web/` files with `Cache-Control: no-cache` plus an ETag (mtime and size) and Last-Modified, and answers a matching `If-None-Match` / `If-Modified-Since` with a 304, so refreshes don't re-download unchanged files (the 1.2 MB Greg background included). `/api/bettors/reset` also checks the `X-Admin-Password` header.
- `tracker.py` is the 5-stack detection (the module docstring explains the algorithm). Each sync fetches every member's *stored matches* (one API call per member). A match id seen for all members on the same team counts as a game. A match missing exactly one member is checked against the v4 match-details endpoint. Everything else goes into the `rejected_matches` meta key and is never re-checked. Polling runs on a daemon thread (`start()`/`_loop`), and `/api/sync` triggers `request_sync()` on another thread. When a sync records new matches, it calls the `on_new_matches` callback, which is where bets get settled.
- `henrik.py` is a thin urllib client with a global minimum request interval, rate-limit header tracking and automatic 429 backoff. Stay inside the budget of about 30 requests per minute (`details_per_sync` caps enrichment fetches).
- `db.py`: one shared `sqlite3` connection (`check_same_thread=False`, WAL) guarded by an `RLock`. The poller thread and the request threads all go through it. Multi-step writes (balance adjustment + bet insert/update) wrap `with db.lock:`. The schema is `CREATE TABLE IF NOT EXISTS` only, with no migrations, so a column added to an existing table won't reach an existing `data/tracker.db` unless you add migration logic. The `meta` table is a JSON key/value store (`cookie_secret`, `rejected_matches`, `last_sync`, `backfilled`, `history_backfilled`).
- `member_games` holds each member's own line from every stored match in a counted mode, 5-stack or not. `db.baseline_rows()` returns the rows whose `match_id` is not in `matches` (the member's non-5-stack games). Sync always inserts these rows with `INSERT OR IGNORE`, and `history_backfilled` forces one full fetch on databases that predate the table.
- `stats.py`: pure aggregation over DB rows. `deviation()` compares a member's 5-stack rows with their baseline rows (pooled values plus a two-sample z statistic → verdicts shown on the Players page). `player_metrics()` defines the per-game stat values (ACS, ADR, HS%, and so on), and both `stats.py` and bet settlement use it, so a change there alters both the displayed stats and settlement results.
- `insights.py`: `build_insights(db)` shapes every dataset for the Charts tab (`/api/insights`): chronological games with session number, rolling form, damage share (per game and the running all-time `damage_cum`) and role-comp key; close/blowout/momentum records; per-player map, win-vs-loss and aim splits; bettor profit series. Keep aggregation here, where the self-test covers it. The only thing binned in the browser is the day × time-of-day heatmap, because it needs the viewer's local time zone. `ROLES` maps agents to roles, so add new agents there.
- `rewards.py`: `RewardManager.pay_for_match()` runs from `App.on_new_matches` after bet settlement. For every game it pays each member `game_reward` (plus optional `win_reward` for a win) and a performance bonus of up to `performance_bonus_max`. The bonus is the share of the member's own earlier 5-stack games (`db.player_rows()` from before this match, not the non-5-stack baseline) that this game's ACS beats, and it is half the maximum when there are fewer than 5 baseline games. It is rounded to the nearest `BONUS_STEP` (5). Rewards go to the bettor account named by `members[].bettor` in config.json, else by the nickname's entry in the committed `bettor_names.json` (loaded by `config.load_bettor_names()`), else the nickname itself. The account is created unclaimed if missing. The `rewards` table has one row per member per game, so re-syncs never pay twice. `db.pay_reward` records the row and credits the balance in one transaction. Games that started before meta `rewards_since` never pay. Leaderboard profit and ROI subtract rewards, so they stay betting-only. A season reset (`BetManager.reset` → `db.archive_and_reset`, one transaction) first saves the leaderboard, every bet and every reward into `seasons`, `archived_bets` and `archived_rewards`, then clears bets and rewards and resets balances. `/api/bettors/reset` also requires `{"confirm": "RESET"}`, and the Bettors tab shows past seasons from `/api/seasons`.
- `timeline.py`: `extract_timeline(v4_record, member_puuids)` keeps a compact copy of a match's rounds (winner, plant site and planting team, defuse) and kills (round, time, killer, victim, weapon), plus each player's team. It is stored as JSON in `match_timelines`: NULL if the record had no round data or 404'd, which also stops refetching. The tracker saves it whenever it fetches a full record, and `db.matches_needing_details()` also returns games without a timeline, so history backfills `details_per_sync` games per sync. `clutches_and_multikills()` and `spike_sites()` work on these timelines; attack/defence sides are inferred from which team planted, per half. Parsing is defensive because the v4 layout isn't ours. `insights.py` also builds the agent pool (`players[].agents`) and `rounds` from these timelines. `insights.betting_report(db, bettor_of)` (served at `/api/betting-report`) builds the Bettors tab's betting cards: the report card (ROI by market type, bets on yourself vs others) and the profit-over-time series (`bankroll`). `bettor_of` maps each member to their bettor account for "on yourself". Its `accuracy` (`insights.odds_accuracy(db, edge)`) checks the odds against results: each settled single or parlay leg (one per game, market and selection, voids left out) pairs the model's chance before the house edge (`fair_prob`, saved on bets since this card; older bets fall back to `odds.fair_chance()`, which divides the edge back out of the price) with whether it won, grouped into chance bins and market types with a verdict from the z score of wins against expected wins. `FiveViz.bettingReport()` in `viz.js` draws the report card and the profit chart, `FiveViz.oddsAccuracy()` draws the odds accuracy card at the bottom of the Bettors tab, and all are mounted like the charts.
- `forecasts.py`: `build_forecasts(db, engine, stat, puuid)` (served at `/api/forecasts`) replays the odds engine over history for the Forecasts tab. Each complete 5-stack game (once the player has `MIN_PRIOR` earlier ones) is predicted from that player's earlier games only, through `OddsEngine.samples()` (the recency / map / agent weighting and forfeit scaling that `build()` uses) and `OddsEngine.stat_range()`: from the same smoothed distribution as the over/under lines, a range cut at its percentiles to hold `COVERAGE` of games (`kde_quantile`, so it's lopsided for skewed stats), the typical game (its median, near the line) and the expected value (its mean). A game's expected value equals the player-prop mean the odds board showed before it, and changes to the odds weighting show up here too. "Average vs forecast" and the grid use the mean, so a calibrated forecast averages out to zero even on skewed stats; better / worse compare against the range. Only the picked player is replayed; the rest just get a `forecast_games` count for the picker. Besides the priced stats it forecasts kills, deaths and assists per round (`kpr`/`dpr`/`apr` from `player_metrics()`, with their own smoothing floors in `forecasts.PER_ROUND`), which take game length out. Results are grouped into map × role cells (`insights.ROLES`) plus map and role totals, with the agents inside each cell; one stat per request, full detail for one player.
- `recap.py`: `build_recap(db, engine, match_id, bettor_of, bonus_max)` (served at `/api/recap`) builds the Matches tab's recap of one game: header (night, older / newer ids), scoreboard (this game against the player's `usual` earlier complete games and `forecasts.forecast_one()`), round by round from the stored timeline (`_round_story`: running score, side via `timeline.first_half_attackers`, first bloods, multi-kills, clutches, knife and team kills), the game's settled bets and rewards, and ranked `highlights`. Each highlight is `_hl(score, kind, title, detail, puuid, tone)`: score ranks them (90+ once-in-a-season, 50-70 worth a mention, under 40 trivia), tone is good / bad / odd / info. They come from `_player_highlights` (records at the precision shown via `_shown`, near-records, long runs, agent / map bests, firsts, rank, milestones, top-fragger streaks, one forecast surprise, timeline events), `_game_line_highlights`, `_round_highlights`, `_squad_highlights` and `_betting`. History is always games *before* this one; "record" and "first" claims need `MIN_RECORD_GAMES` earlier games. New highlight ideas go in the matching function with a self-test case in the "recap" section.
- `gamestate.py`: `ending(match)` reads how a game ended from its score: complete (a team reached the mode's rounds-to-win target), forfeit (a surrender: stopped short after more than 4 rounds), or no contest (a remake within the first 4 rounds). The tracker never records no-contest games, and keeps them out of `member_games`. Forfeits are recorded, and v4 `teams[].won` overrides the score for the result. `bets._evaluate` settles a forfeit's non-match-result markets only if they were already decided (an over on a counting stat already past the line), and voids the rest. Parlays get this for free, because `_evaluate_parlay` runs each leg through `_evaluate`, so a surrender-voided leg is dropped like any void leg. `odds.py` scales a forfeit's counting stats to `full_game_rounds()` and weights it by the share of a game played. The total-rounds market excludes forfeits.
- `odds.py`: `OddsEngine.build(db, context)` recomputes the whole odds board on each call. It is stateless and uses recency-weighted samples, boosted by the chosen map/agent in `context`. Market ids are strings: `ou:<stat>:<puuid>`, `top:<stat>`, `low:<stat>`, `team:win`, `team:rounds`, `team:ot` (overtime yes/no, `gamestate.went_to_overtime`), `team:rw` / `team:rl` (rounds won / lost over-under), `team:margin` and `team:score` (only squad wins are offered: margins `w1-2` / `w3-5` / `w6+`, overtime counting as 1-2, and regulation scores `13-0`..`13-11`; a loss, or an overtime win for exact score, just loses). The last four come from `score_model(p_win, p_ot)` (cached): a final-score distribution from a per-round win chance that varies by game (normal, `mu` / `sd`), tuned so it matches the match-result chance and gets as close as it can (sd up to `SCORE_SD_MAX`) to the overtime chance; `score_key()` / `margin_key()` map a finished game to its selection, and `MULTI_WAY` markets (top, margin, exact score) carry double the edge in `market_overround()`. Each `TOP_DEFS` entry makes a "top" market and its counter ("low", the bottom of the scoreboard) from the same Monte Carlo draws. Both have `type: "top"`, and are told apart by `direction` ("high"/"low"), which `place`/`place_parlay` store in the bet's meta and `_evaluate` uses to pick max or min; old bets without it are "high". `acs_rel` ("Popped off"/"Got diff'd") is ACS ÷ the player's own pooled ACS: over their whole history in the odds, and over games before the match at settlement (`BetManager._add_relative_acs`). `find_market()` looks them up. Custom lines: `build(db, context, alts=[(stat, puuid, line)])` also prices those under `board["custom"]` via `alt_market()` (same KDE and edge as `ou_market`, market id `alt:<stat>:<puuid>:<line>`, parsed by `parse_alt()`), each selection `available` only when its fair chance is within `ALT_MIN_CHANCE`..`ALT_MAX_CHANCE`, with `limits` for the page. They're `type: "ou"`, so settlement needs nothing new; `bets.place()` / `place_parlay()` pass the alt ids to `build()`, and a parlay allows one line per player and stat (`alt_family()`). `/api/odds/custom` quotes one for the Custom line card in `bets.js`. Exact numbers (`exact:<stat>:<puuid>:<N>`, `type: "exact"`, counting stats only) ride the same path: `parse_alt()` returns `(stat, puuid, value, kind)`, `build()` prices them with `exact_market()` (the KDE mass between N - 0.5 and N + 0.5, multi-way edge, at least `EXACT_MIN_CHANCE`), `bets._evaluate` settles them on the exact value, and on a surrender they lose once passed and are otherwise void.
- `bets.py`: `place()` rebuilds the board with the bettor's context and locks in the current odds and line on the bet row. `place_parlay()` does the same for 2-10 legs (each from a different market): it stores the legs as a JSON list in the bet's `context` column with `market_type="parlay"`, and the bet's own `odds_decimal` is the product of the legs' decimal odds. `settle_for_match()` settles every pending bet whose `placed_ts` is before the match's `started_ts` plus `bet_grace_minutes` (default 2: Riot's start time is when the match launches, so bets made while loading in still count), whatever the map. `cancel()` lets a bettor cancel only within `bet_cancel_minutes` (default 1) of placing a bet; admin cancels aren't limited; a parlay is settled leg by leg through `_evaluate_parlay()` (reusing `_evaluate()` per leg), which writes each leg's result back into `context` for the UI. The score markets (`SCORE_MARKETS`) settle from the final score, are void outside first-to-13 modes and on a surrender (rounds won / lost settle there if already past the line, like total rounds). `mark_streaks(board)` (applied to `/api/odds`) settles every board pick at today's line against the last `STREAK_LOOKBACK` games through `_evaluate()` and gives a `streak` count to the ones that won at least `STREAK_MIN` (3) in a row, voids skipped, and a `cold` count to roughly 50/50 picks (fair chance within `COLD_CHANCE`) that lost as many, in markets with three or more picks only (in a two-way market the other side already has the flame); `oddBtn()` in `app.js` gives those buttons the `hot` or `cold` class, an animated flame or frost border in `style.css`. Void results (landing exactly on the line, ties, draws) refund the stake; a void leg inside a parlay is just dropped from the payout math instead, and the whole parlay only voids if every leg does.
- `tunnel.py` downloads `cloudflared` into `tools/` and runs it as a child process. It refuses to start without `site_password`.
- `web/app.js`: a single IIFE SPA with views `overview/players/forecasts/viz/odds/bettors/matches/setup` (the nav calls `viz` "Charts"; Setup has no tab, it's the ⚙ button in the top bar; Players and Odds & Bets use the wide container) (the Matches tab shows `FiveRecap.html(state.recap)` above the game list, which is grouped by night (`NIGHT_GAP_S`, the same 3-hour rule as `insights.SESSION_GAP_S`; the latest `NIGHTS_OPEN` open); `state.recapId` picks the game, '' = latest), a global `state` object, and an `api()` fetch helper. The Players tab is one comparison table (`playersTable()`: a row per player over `PLAYER_COLS`, the best per column highlighted, ▲/▼ where the player's last `TREND_RECENT` games differ 5% or more from the `TREND_BEFORE` before them (`trend()`, from `form`), then "5-stack vs. their other games" columns from `deviation`) and one player's detail (`playerDetail()`, picked by row or button into `state.playerPick`: a tile per major stat with a sparkline of the last 15 games and High / Low links to the recaps of their best and worst complete games (`stats._ranges()` → `range`), a best-game tile, all their agents and maps, links to their forecasts and the charts), then a trend chart (`FiveViz.playerTrends()` / `drawTrends()` in `viz.js`, from `stats._timeline()`: every complete game, one line per player for the picked stat, one point per game, every game or just the last 10, players toggled from the legend, and the detail's player (`focus`) drawn bold over the faded rest; `state.trends`). It uses the wide layout, like Odds & Bets. Numbers identical for all five (games, win rate, win rate by map) are left to the Overview. The detail's old "Compared with their other games" table and W/L chips are switched off by `PLAYER_CARD_OTHER_GAMES` / `PLAYER_CARD_FORM` (set to true to bring them back). The Overview is a front page: KPI tiles, the latest game with its top 3 recap highlights (`overviewLastGame`, from its own `/api/recap` fetch in `loadOverview`), your balance, the top bettors and the standout bets settled on the last `OV_BET_GAMES` games (`overviewBetting` / `overviewStandouts`, from won and lost bets fetched in `loadOverview`), who's trending (`overviewTrending`, the Players tab's `trend()`), and map win rates. Long explanations are folded with `how(summary, more)` (a `<details class="how">`: one line, "How this works" for the rest), defined in each of app.js, bets.js, viz.js and recap.js. The top bar's balance chip (`renderMe()`, from `/api/bettor/me`: name and balance only; open stakes show under the bet slip) shows the signed-in bettor on every tab, refreshed on each redraw and with the 20-second status poll. When the balance changes, the one under the bet slip (`#slip .acct-balance`, not the chip) counts to it (`tickBalance()`); through `celebrateWins()`, fires `confetti()` (gold for a win at `LONG_SHOT_DECIMAL` or longer) for `recent_wins` settled after the `fs.seenWins.<name>` marker in `localStorage`, so wins that settle while the site is closed are celebrated on the next visit; the confetti comes out of the bet slip's balance, so it waits until Odds & Bets is showing (and a hidden tab until it's visible), and a first visit only sets the marker. Tickets placed a moment ago (`justPlaced` in `bets.js`) land with a "Placed" stamp in the sidebar's "Your open bets" card only (`myBetsCard()`, under the custom line: the signed-in bettor's open bets in the same slip card as the Open bets section). It remembers the bettor name, odds format, stake and theme in `localStorage`; the ◐ button cycles `data-theme` dark → light → greg (Greg Mode: the light theme's colours over `web/assets/greg.png`, stretched to the window width and fixed in place while the page scrolls (a `position: fixed` `body::before` layer, since `background-attachment: fixed` is ignored on iOS), the top-left logo swapped from `onkey-logo.png` to `greg-logo.png` by CSS, every click dropping a `greg-drop.png` that falls off the screen (the `greg-fall` animation; capped at 25, off for reduced motion), with `--surface` / `--surface-2` at 50% opacity so every panel is see-through; tooltips and toasts stay solid). `bettorSlot()` colours a bettor like the squad member whose account it is (`/api/status` members carry `bettor`, from `RewardManager.account_name`).
- `web/bets.js` (`window.FiveBets`) holds the betting UI: the bet slip, bet tickets, the Bettors tab (`viewBettors()`, reset panel, rewards, past seasons) and the bet/report/season loaders. `app.js` calls `FiveBets.init({state, api, draw, ...})` once to hand over its shared state and helpers, destructures the functions it calls (`betsSection`, `slipHtml`, `viewBettors`, `loadBets`, ...), and calls `FiveBets.bind(view)` from its own `bind()` to wire the betting buttons after each redraw. It loads before `app.js` in `index.html`. On the Odds & Bets tab, `betsSection()` shows open bets grouped by bettor into ticket-styled "slip" cards (`bettorSlips()`/`betTicket()`, totals from `betTotals()`). The Bettors tab's `settledSection()` shows settled bets for `SETTLED_GAMES` games (1; it was 3) starting from the game picked in its dropdown (`state.settledGame`, '' = the most recent) via `gameSlips()`, grouped per game and then per bettor. The dropdown lists the games among the bets loaded (`/api/bets?limit=600`). `/api/bets` rows carry the settled game's `game_map`/`game_rounds_won`/`game_result`/`game_started_ts`, and a parlay bet's legs (parsed from its `context` JSON) render nested inside the ticket. The bet slip (`slipHtml()`) shows a Singles/Parlay toggle once 2+ picks are queued; in parlay mode it posts `{legs, stake, context}` to `/api/bets` instead of one request per pick.
- `web/recap.js` (`window.FiveRecap`) renders the recap cards (header, highlights, scoreboard, round strip, betting and rewards); its hover details use the charts' `data-tip` tooltips, so `app.js` calls `FiveViz.mount` on the Matches tab too.
- `web/viz.js` (`window.FiveViz`) draws the Charts tab as hand-built SVG/HTML charts, and the Forecasts tab (`FiveViz.forecasts(data, helpers, pick)`; `app.js` keeps the picked stat, player and map|role cell in `state.fc` and refetches on a stat or player change). `html()` returns the cards with empty `[data-chart]` slots, and `mount()` draws each slot at its real pixel width and redraws on resize. Chart colors are CSS variables in `style.css` (`--s1…--s8` per player slot, plus `--div-*`, `--aim-*`, `--pair-*`, `--axis`), defined in all three theme blocks, so the theme toggle needs no redraw. Tooltip specs sit in `data-tip` JSON and are rendered with `textContent`. Each chart card can also get a "Show as table" view (`table()`), switched off by `SHOW_TABLES = false` in `viz.js`; set it to true to bring them all back (Charts, Bettors and Forecasts). The Charts tab's buttons pick a genre (`GENRES`, `html(d, helpers, genre)`, `state.vizGenre`): all, results, players or rounds, each with its own layout, and only that genre's charts are drawn.

`config.json`, `data/` and `tools/` are gitignored. Delete `data/tracker.db` to rebuild history from scratch.
