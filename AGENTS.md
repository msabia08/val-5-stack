# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is a copy of this file for other AI coding agents (such as Codex), identical except for its `# AGENTS.md` title. After changing this file, rebuild it with `{ echo "# AGENTS.md"; tail -n +2 CLAUDE.md; } > AGENTS.md`; CI fails if the two differ below the title.

## What this is

A local website that tracks a Valorant 5-stack through the unofficial HenrikDev API, keeps per-player stats for games where all five members were on the same team, and generates sportsbook-style odds that the squad bets on with virtual credits. `README.md` covers the user-facing behaviour and every `config.json` key.

**Hard constraint:** Python 3.10+ standard library only, with no third-party packages. The frontend (`web/`) is plain JS/CSS/HTML with no build step and no dependencies. Keep it that way.

**Screens and theme:** the site is built around one screen size, a 1920×1080 desktop (the most common screen among PC gamers, which the squad is); don't spend effort on other widths, including phone, tablet and small-laptop layouts, and check UI changes at 1920×1080. Dark is the default theme whatever the OS prefers (no `prefers-color-scheme` handling); light and the shop themes apply only when picked with the ◐ button (`data-theme`, saved in `fs.theme`). Design and review UI in dark mode first. `docs/DESIGN.md` is the design guide (layout, colour tokens, type, shared components, wording, how to check a UI change, and the open UI backlog): follow it for any change in `web/`, and update it when you add or retire a pattern.

## Commands

```
python server.py                  # run (needs config.json; created from config.example.json on first run)
python server.py --demo           # synthetic data in data/demo.db, never calls the API
python server.py --no-browser --port=8090 --no-tunnel --config=other.json
python server.py --tunnel         # also publish via Cloudflare quick tunnel (requires site_password)
python tests/selftest.py          # the only test suite: offline, end-to-end, prints "selftest OK" (CI runs it on 3.10 and 3.12)
```

Line endings are LF, enforced by `.gitattributes` (`.bat` files are CRLF); write new files with LF.

Keep the code runnable on Python 3.10 (the README's minimum; CI checks it): for example, no reusing an f-string's own quote character inside `{…}` (3.12+ only).

Don't pipe `tests/selftest.py` into `head`: the closed pipe makes the tracker's `print` raise `OSError` on Windows. Redirect to a file instead.

There is no linter config, no test framework and no single-test runner. `tests/selftest.py` is a series of named sections (`@section("forfeits")` functions) run in order against a `FakeClient` that stands in for `HenrikClient`; each prints `ok: <name>`, and a failure prints the traceback, then `FAIL: <name>`, and stops. The sections share one database and a `shared` namespace (bets placed in "bets" are settled in "settlement"), so they can't run on their own; anything a later section needs goes on `shared`. Add new checks to the matching section or a new one, and extend `FakeClient` when new API calls are involved. It also fails if a key in `config.example.json` is missing from the README's configuration table. `HENRIK_API_KEY` in the environment overrides `api_key` from the config.

## Branches and pull requests

Several people push to this repository (`msabia08/val-5-stack`), so every change goes through a pull request into `main`; never commit to `main` directly. AI agents commit, push and open pull requests only when asked.

1. `git fetch`, then branch off the latest `origin/main` with a short kebab-case name for the change (`forfeit-handling`, `scoreboard-counters`). Branches live in this repository, not in forks.
2. Before committing, run the self-test and `for f in web/*.js; do node --check "$f"; done`, and check anything visible in the browser with `python server.py --demo` (no console errors). Update `docs/DATA.md`, `docs/DESIGN.md` (for UI changes), the README and this file (then rebuild `AGENTS.md`) as `.github/pull_request_template.md` lists.
3. Commit with a short imperative summary line and a body that says what changed and why.
4. `git push -u origin <branch>`, then `gh pr create --base main` with the template's Summary and a ticked Test plan.
5. CI (`.github/workflows/selftest.yml`) must pass: `gh pr checks <number> --watch`. Pull requests are merged with a merge commit ("Merge pull request #N"), not squashed.

If `main` moves while a branch is open, merge `origin/main` into the branch rather than rebasing, and never force-push a branch that's already pushed. Work that builds on an unmerged pull request branches from that pull request's branch, and its pull request targets that branch (`gh pr create --base <first-branch>`) so the diff shows only the new work. Merge the first one, then switch the second to `main` (`gh pr edit <number> --base main`; GitHub does this by itself if the first branch was deleted on merge).

## Architecture

`docs/DATA.md` is the data reference: HenrikDev response structures (captured from real responses with `scripts/inspect_henrik.py`), every database table, every `/api/*` endpoint, and API data we don't use yet. Check it before assuming a field exists, and update it when you add a table, column or endpoint.

The data flows one way: **HenrikDev → tracker → SQLite → stats/odds → JSON API → SPA**, and bets feed back in at settlement.

All backend code lives in the `fivestack/` package and imports its siblings relatively (`from .db import DB`). The root `server.py` is only a launcher for `fivestack.app.main`. `fivestack/config.py` defines `ROOT` as the repository root, and `web/`, `data/`, `tools/` and `config.json` are resolved from it, so they stay at the top level.

- `fivestack/app.py` wires everything together. `fivestack/config.py` loads and validates `config.json`, and `fivestack/auth.py` holds the password and bettor-session cookie logic. `App` owns one instance each of `DB`, `OddsEngine`, `BetManager`, `RewardManager`, `BananaManager`, `ArcadeManager`, `SlotManager`, `Auth`, `Tunnel`, and (only when the config is valid and not in demo mode) `HenrikClient` + `Tracker`. `Handler` is a stdlib `BaseHTTPRequestHandler` that routes by hand in `do_GET`/`_api_get`/`do_POST`/`do_DELETE`. New endpoints go there. Every route except `/login`, `/logout`, `/style.css` and `/assets/*` (images, which the login page shows too) sits behind the cookie check when `site_password` is set. `_static()` serves `web/` files with `Cache-Control: no-cache` plus an ETag (mtime and size) and Last-Modified, and answers a matching `If-None-Match` / `If-Modified-Since` with a 304, so refreshes don't re-download unchanged files (the 1.2 MB Greg background included). `/api/bettors/reset` also checks the `X-Admin-Password` header.
- `tracker.py` is the 5-stack detection (the module docstring explains the algorithm). Each sync fetches every member's *stored matches* (one API call per member). A match id seen for all members on the same team counts as a game. A match missing exactly one member is checked against the v4 match-details endpoint. Everything else goes into the `rejected_matches` meta key and is never re-checked. Polling runs on a daemon thread (`start()`/`_loop`), and `/api/sync` triggers `request_sync()` on another thread. When a sync records new matches, it calls the `on_new_matches` callback, which is where bets get settled.
- `henrik.py` is a thin urllib client with a global minimum request interval, rate-limit header tracking and automatic 429 backoff. Stay inside the budget of about 30 requests per minute (`details_per_sync` caps enrichment fetches).
- `db.py`: one shared `sqlite3` connection (`check_same_thread=False`, WAL) guarded by an `RLock`. The poller thread and the request threads all go through it. Multi-step writes (balance adjustment + bet insert/update) wrap `with db.lock:`. The schema is `CREATE TABLE IF NOT EXISTS` only, with no migrations, so a column added to an existing table won't reach an existing `data/tracker.db` unless you add migration logic. The `meta` table is a JSON key/value store (`cookie_secret`, `rejected_matches`, `last_sync`, `backfilled`, `history_backfilled`).
- `member_games` holds each member's own line from every stored match in a counted mode, 5-stack or not. `db.baseline_rows()` returns the rows whose `match_id` is not in `matches` (the member's non-5-stack games). Sync always inserts these rows with `INSERT OR IGNORE`, and `history_backfilled` forces one full fetch on databases that predate the table.
- `stats.py`: pure aggregation over DB rows. `deviation()` compares a member's 5-stack rows with their baseline rows (pooled values plus a two-sample z statistic → verdicts shown on the Players page). `player_metrics()` defines the per-game stat values (ACS, ADR, HS%, and so on), and both `stats.py` and bet settlement use it, so a change there alters both the displayed stats and settlement results.
- `insights.py`: `build_insights(db)` shapes every dataset for the Charts tab (`/api/insights`): chronological games with session number, rolling form, damage share (per game and the running all-time `damage_cum`) and role-comp key; close/blowout/momentum records; per-player map, win-vs-loss and aim splits; bettor profit series. Keep aggregation here, where the self-test covers it. The only thing binned in the browser is the day × time-of-day heatmap, because it needs the viewer's local time zone. `ROLES` maps agents to roles, so add new agents there.
- `rewards.py`: `RewardManager.pay_for_match()` runs from `App.on_new_matches` after bet settlement. For every game it pays each member `game_reward` (plus optional `win_reward` for a win) and a performance bonus of up to `performance_bonus_max`. The bonus is the share of the member's own earlier 5-stack games (`db.player_rows()` from before this match, not the non-5-stack baseline) that this game's ACS beats, and it is half the maximum when there are fewer than 5 baseline games. It is rounded to the nearest `BONUS_STEP` (5). Rewards go to the bettor account named by `members[].bettor` in config.json, else by the nickname's entry in the committed `bettor_names.json` (loaded by `config.load_bettor_names()`), else the nickname itself. The account is created unclaimed if missing. The `rewards` table has one row per member per game, so re-syncs never pay twice. `db.pay_reward` records the row and credits the balance in one transaction. Games that started before meta `rewards_since` never pay. Leaderboard profit and ROI subtract rewards, so they stay betting-only. A season reset (`BetManager.reset` → `db.archive_and_reset`, one transaction) first saves the leaderboard, every bet, every reward and every transfer into `seasons`, `archived_bets`, `archived_rewards` and `archived_transfers`, then clears bets, rewards and transfers and resets balances.
- Transfers: `BetManager.send()` (`POST /api/transfers`, signed-in bettor only) moves credits from one bettor to another; `db.transfer()` checks the sender's balance and moves both balances plus the `transfers` row in one transaction. Leaderboard profit also subtracts net transfers received (`db.transfer_totals()`, generosity tax included, shown as its own `transfers` column), so it stays betting-only. The generosity tax ("the generous monkey gets rewarded"): a transfer of at least `TAX_MIN_TRANSFER` (250) opens a tax (`tax_status='open'`, one per sender and recipient, decided inside `db.transfer()`), and `BetManager.collect_taxes()`, run at the end of `settle_for_match()`, takes `TAX_RATE` (10%) of the net winnings of each taxed bettor's biggest winning bet on that game for every sender with an open tax made before the settlement (`db.open_taxes()`), through `db.pay_tax()` (both balances, the transfer row and a note on the bet, one transaction). `/api/status` carries `tax_rate` / `tax_min_transfer` for the page, and `announceTaxes()` in `app.js` toasts taxes collected (`/api/bettor/me` `recent_taxes`, marker `fs.seenTax.<name>`). The Standings page's Send credits card (`transferCard()` / `bindTransfers()` in `bets.js`, form state in `state.transfer`) asks for a second click on a confirm line before sending, and `announceTransfers()` in `app.js` toasts transfers received (`/api/bettor/me` `recent_received`) since the `fs.seenTransfers.<name>` marker in `localStorage`. `/api/bettors/reset` also requires `{"confirm": "RESET"}`, and the Standings page shows past seasons from `/api/seasons`.
- `timeline.py`: `extract_timeline(v4_record, member_puuids)` keeps a compact copy of a match's rounds (winner, plant site and planting team, defuse) and kills (round, time, killer, victim, weapon), plus each player's team. It is stored as JSON in `match_timelines`: NULL if the record had no round data or 404'd, which also stops refetching. The tracker saves it whenever it fetches a full record, and `db.matches_needing_details()` also returns games without a timeline, so history backfills `details_per_sync` games per sync. `clutches_and_multikills()` and `spike_sites()` work on these timelines; attack/defence sides are inferred from which team planted, per half. Parsing is defensive because the v4 layout isn't ours. `insights.py` also builds the agent pool (`players[].agents`) and `rounds` from these timelines. `insights.betting_report(db, bettor_of)` (served at `/api/betting-report`) builds the Standings page's betting cards: the report card (ROI by market type, bets on yourself vs others) and the profit-over-time series (`bankroll`). `bettor_of` maps each member to their bettor account for "on yourself". Its `accuracy` (`insights.odds_accuracy(db, edge)`) checks the odds against results: each settled single or parlay leg (one per game, market and selection, voids left out) pairs the model's chance before the house edge (`fair_prob`, saved on bets since this card; older bets fall back to `odds.fair_chance()`, which divides the edge back out of the price) with whether it won, grouped into chance bins and market types with a verdict from the z score of wins against expected wins. `FiveViz.bettingReport()` in `viz.js` draws the report card and the profit chart, `FiveViz.oddsAccuracy()` draws the odds accuracy card at the bottom of the Standings page, and all are mounted like the charts.
- `forecasts.py`: `build_forecasts(db, engine, stat, puuid)` (served at `/api/forecasts`) replays the odds engine over history for the Forecasts tab. Each complete 5-stack game (once the player has `MIN_PRIOR` earlier ones) is predicted from that player's earlier games only, through `OddsEngine.samples()` (the recency / map / agent weighting and forfeit scaling that `build()` uses) and `OddsEngine.stat_range()`: from the same smoothed distribution as the over/under lines, a range cut at its percentiles to hold `COVERAGE` of games (`kde_quantile`, so it's lopsided for skewed stats), the typical game (its median, near the line) and the expected value (its mean). A game's expected value equals the player-prop mean the odds board showed before it, and changes to the odds weighting show up here too. "Average vs forecast" and the grid use the mean, so a calibrated forecast averages out to zero even on skewed stats; better / worse compare against the range. Only the picked player is replayed; the rest just get a `forecast_games` count for the picker. Besides the priced stats it forecasts kills, deaths and assists per round (`kpr`/`dpr`/`apr` from `player_metrics()`, with their own smoothing floors in `forecasts.PER_ROUND`), which take game length out. Results are grouped into map × role cells (`insights.ROLES`) plus map and role totals, with the agents inside each cell; one stat per request, full detail for one player. The player also gets `next`, the forecast for their next game from all their games so far (`forecast_one()` on a row with the odds board's map and agent, passed as `map` / `agent` by `loadForecasts()`), so its expected value is the player-prop mean the board shows.
- `recap.py`: `build_recap(db, engine, match_id, bettor_of, bonus_max)` (served at `/api/recap`) builds the Matches tab's recap of one game: header (night, older / newer ids), scoreboard (this game against the player's `usual` earlier complete games and `forecasts.forecast_one()`), round by round from the stored timeline (`_round_story`: running score, side via `timeline.first_half_attackers`, first bloods, multi-kills, clutches, knife and team kills), the game's settled bets and rewards, and ranked `highlights`. Each highlight is `_hl(score, kind, title, detail, puuid, tone)`: score ranks them (90+ once-in-a-season, 50-70 worth a mention, under 40 trivia), tone is good / bad / odd / info. They come from `_player_highlights` (records at the precision shown via `_shown`, near-records, long runs, agent / map bests, firsts, rank, milestones, top-fragger streaks, one forecast surprise, timeline events), `_game_line_highlights`, `_round_highlights`, `_squad_highlights` and `_betting`. History is always games *before* this one; "record" and "first" claims need `MIN_RECORD_GAMES` earlier games. New highlight ideas go in the matching function with a self-test case in the "recap" section.
- `gamestate.py`: `ending(match)` reads how a game ended from its score: complete (a team reached the mode's rounds-to-win target), forfeit (a surrender: stopped short after more than 4 rounds), or no contest (a remake within the first 4 rounds). The tracker never records no-contest games, and keeps them out of `member_games`. Forfeits are recorded, and v4 `teams[].won` overrides the score for the result. `bets._evaluate` settles a forfeit's non-match-result markets only if they were already decided (an over on a counting stat already past the line), and voids the rest. Parlays get this for free, because `_evaluate_parlay` runs each leg through `_evaluate`, so a surrender-voided leg is dropped like any void leg. `odds.py` scales a forfeit's counting stats to `full_game_rounds()` and weights it by the share of a game played. The total-rounds market excludes forfeits.
- `moments.py`: `game_facts(match, timeline)` is the one place the round "moment" facts come from (pistol won, ahead after `HALF` rounds (none in Swiftplay / Spike Rush or a game that stopped earlier), an ace by one of us, a comeback from `COMEBACK_DOWN` behind to a win, flawless rounds won with no squad deaths); each is None when the timeline can't tell. `odds.moment_markets()` prices them from history and `bets._evaluate_moment()` settles on them, so a change here moves both.
- `odds.py`: `OddsEngine.build(db, context)` recomputes the whole odds board on each call. It is stateless and uses recency-weighted samples, boosted by a map/agent in `context` when one is given (the Place bets page has no map or agent pickers any more, so it never sends one). Player props (`ou:<stat>:<puuid>`, custom lines and exact numbers) exist only for `PROP_KEYS` (kills, deaths, assists, HS%); ACS and ADR are not props, though ACS still drives the top / bottom of the scoreboard markets. Market ids are strings: `ou:<stat>:<puuid>`, `top:<stat>`, `low:<stat>`, `team:win` (its `basis.recent` is the last five results, newest first, for the form chips), `team:ot` (overtime yes/no, `gamestate.went_to_overtime`), `team:margin` and `team:score` (every result: margins `l6+` / `l3-5` / `l1-2` / `w1-2` / `w3-5` / `w6+`, overtime counting as 1-2, and scores `0-13`..`11-13`, `ot-loss`, `ot-win`, `13-11`..`13-0`, in that order), and the round "moment" markets from `moment_markets()` (`MOMENT_DEFS`: `team:pistol`, `team:half`, `team:ace`, `team:comeback` yes / no and `team:flawless` over / under, `type: "team_moment"`, offered once `MOMENT_MIN_GAMES` (5) games have a timeline; a yes / no price is the recency-weighted hit rate pulled toward the def's `prior` by 2 pseudo-games). `team:rounds` (total rounds) and `team:rw` / `team:rl` (rounds won / lost) are no longer on the board, but old bets on them still settle. Margin and exact score come from `score_model(p_win, p_ot)` (cached): a final-score distribution from a per-round win chance that varies by game (normal, `mu` / `sd`), tuned so it matches the match-result chance and gets as close as it can (sd up to `SCORE_SD_MAX`) to the overtime chance; `score_key()` / `margin_key()` map a finished game to its selection, and `MULTI_WAY` markets (top, margin, exact score) carry double the edge in `market_overround()`. Each `TOP_DEFS` entry makes a "top" market and its counter ("low", the bottom of the scoreboard) from the same Monte Carlo draws. Both have `type: "top"`, and are told apart by `direction` ("high"/"low"), which `place`/`place_parlay` store in the bet's meta and `_evaluate` uses to pick max or min; old bets without it are "high". `acs_rel` ("Popped off"/"Got diff'd") is ACS ÷ the player's own pooled ACS: over their whole history in the odds, and over games before the match at settlement (`BetManager._add_relative_acs`). `find_market()` looks them up. Custom lines: `build(db, context, alts=[(stat, puuid, line)])` also prices those under `board["custom"]` via `alt_market()` (same KDE and edge as `ou_market`, market id `alt:<stat>:<puuid>:<line>`, parsed by `parse_alt()`), each selection `available` only when its fair chance is within `ALT_MIN_CHANCE`..`ALT_MAX_CHANCE`, with `limits` for the page. They're `type: "ou"`, so settlement needs nothing new; `bets.place()` / `place_parlay()` pass the alt ids to `build()`, and a parlay allows one line per player and stat (`alt_family()`). `/api/odds/custom` quotes one for the Custom line card in `bets.js`. Exact numbers (`exact:<stat>:<puuid>:<N>`, `type: "exact"`, counting stats only) ride the same path: `parse_alt()` returns `(stat, puuid, value, kind)`, `build()` prices them with `exact_market()` (the KDE mass between N - 0.5 and N + 0.5, multi-way edge, at least `EXACT_MIN_CHANCE`), `bets._evaluate` settles them on the exact value, and on a surrender they lose once passed and are otherwise void.
- `bets.py`: `place()` rebuilds the board with the bettor's context and locks in the current odds and line on the bet row. `place_parlay()` does the same for 2-10 legs (each from a different market) at the price from `quote_parlay()` (also served at `POST /api/odds/parlay` for the bet slip): it stores the legs as a JSON list in the bet's `context` column with `market_type="parlay"`, each with its `hist` from `leg_history()` (the leg settled through `_evaluate()` at its line on the last `parlay.LOOKBACK` games, via `_recent_games()`, which `mark_streaks()` shares), plus the price as `corr`. `settle_for_match()` settles every pending bet whose `placed_ts` is before the match's `started_ts` plus `bet_grace_minutes` (default 2: Riot's start time is when the match launches, so bets made while loading in still count), whatever the map. `cancel()` lets a bettor cancel only within `bet_cancel_minutes` (default 1) of placing a bet; admin cancels aren't limited; a parlay is settled leg by leg through `_evaluate_parlay()` (reusing `_evaluate()` per leg), which writes each leg's result back into `context` for the UI. The score markets (`SCORE_MARKETS`) settle from the final score, are void outside first-to-13 modes and on a surrender (rounds won / lost settle there if already past the line, like total rounds). Moment bets go through `_evaluate_moment()`, which reads the game's facts from its stored timeline (`settle_for_match()` attaches `db.timeline()`; the tracker fetches it in the same sync) and voids with `NO_ROUND_DATA` when there's none; on a surrender a fact already true stands and the rest void. `mark_streaks(board)` (applied to `/api/odds`) settles every board pick at today's line against the last `STREAK_LOOKBACK` games through `_evaluate()` and gives a `streak` count to the ones that won at least `STREAK_MIN` (3) in a row, voids skipped, and a `cold` count to roughly 50/50 picks (fair chance within `COLD_CHANCE`) that lost as many, in markets with three or more picks only (in a two-way market the other side already has the flame); `oddBtn()` in `app.js` gives those buttons the `hot` or `cold` class, an animated flame or frost border in `style.css`. On the page (`viewOdds()`), the team markets are the match result (`.tm-match`: Win and Loss buttons either side of a bar split by each side's chance, centred, with the last five results as W / L chips under its middle, `.tm-form`), then a grid of question cards (`qcard()`, `.tm-qgrid` / `.tm-q`: the question and its picks; a fact line from the market's `basis` under each, replaced by the streak when there is one, is switched off by `TM_FACTS = false`, along with the final score's overtime label and likeliest line), ending with the final score as a "mountain" (`.tm-mountain`: every score from 0-13 to 13-0 as a column whose bar height is its chance, overtime in the middle, the likeliest outlined). Void results (landing exactly on the line, ties, draws) refund the stake; a void leg inside a parlay is just dropped from the payout math instead (the legs that stood are re-priced with `parlay.correlation()` on their saved `hist`), and the whole parlay only voids if every leg does.
- `parlay.py`: parlay pricing, pure functions. `score_conflict(legs, evaluate)` settles every team leg (all of them are decided by the final score) on each possible first-to-13 score (`FINAL_SCORES`, overtime up to 20-18) and refuses a pair where one leg's winning scores are inside the other's ("13-5" + "Win") or the two never overlap. `correlation(hists)` compares how often the legs all won together on recent games with how often they would if unrelated: pairs at least `LINK_Z` above chance are joined into `linked` groups, each group's joint-win ratio is multiplied in, and the whole parlay's ratio is the fallback; every ratio gets `PRIOR` pseudo-games at 1, fewer than `MIN_GAMES` usable games means no cut, and the `factor` stays between 1 (never boosted) and `MAX_FACTOR`. `price()` divides the multiplied odds by it, never below the longest leg. The slip (`parlayQuoteHtml()` / `fetchParlayQuote()` in `bets.js`) shows the price, marks linked legs and greys out Place for a refused pair; tickets say what linked odds were cut from.
- `bananas.py`: Onkey's Shop's currency, kept apart from credits. `BananaManager.earn()` (`db.earn_bananas`) pays `banana_rate` (0.1) bananas per credit gained, a won bet's profit and every game reward, never taking any back for a loss, so a season's bananas are exactly `banana_rate` × credits won that season. It scans `bets` and `rewards` for gains not paid yet, and `banana_ledger`'s unique `(reason, ref)` stops double payment, so it runs at start-up, at the end of `App.on_new_matches`, after a sign-up and after a season reset. It also grants every account `starting_bananas` (50) once per season (`db.grant_starting_bananas`, reason `starter`, not counted as earned). A wallet is `SUM(delta)` over the ledger. `CATALOG` (cosmetics, one worn per `SLOTS` entry: name colour, badge, title, banner, ticket style, win celebration, theme) and `SOCIAL` (pranks on someone else, active until `expires_ts` and, when `games` > 0, until that many games (`PRANK_GAMES`, 3) have started after them; each `look` says how the page draws it: `cls` on the name, `ticket_cls` on bet tickets, `avatar`, `mark`, or a `kind` (`bounty`, `heckle`, `nick`) that `nameHtml` / `ticketExtras()` draw specially) are code, sorted at import by slot and then price (cheapest first), which is the order every list on the page uses; each item's `look` is what `web/shop.js` draws. `buy()` / `equip()` write only banana tables, never `bettors`, `bets` or `rewards`, and the self-test's "bananas" section asserts the leaderboard is unchanged. `db.archive_and_reset` zeroes every wallet with one `season_reset` row per bettor in the same transaction; owned items stay. `looks()` (in `/api/troop`) is every bettor's worn items and active pranks, which style names across the site.
- `arcade.py`: Onkey's Arcade. `ArcadeManager.start(name, game)` takes `ARCADE_PRICE` (5) bananas (ledger reason `arcade`, counted in `spent`) and returns a one-time token; `finish(name, token, score)` records the score once, for the bettor who paid, within `PLAY_TTL_S`, and only if it fits `GAMES[game]`'s `max_score` and `max_rate` × seconds elapsed (the games run in the browser, so this is a sanity check). The only prize is the board (`board()`: each bettor's best above 0, all time); nothing is paid back and credits are never touched. Game keys are `catch`, `says` and `dash`, the same as in `web/arcade.js`, which draws and runs them.
- `slots.py`: `SlotManager` serves Betting’s Slots page (`GET /api/slots`, `POST /api/slots/spin`). One machine (`MACHINES['jackpot']`, the default when `machine` is omitted) picks each spin's line first (`draw_spin()`, one `secrets.randbelow` ticket out of `tickets`, 100,000): a symbol's triple has its `lines` tickets (fewer for bigger payouts), and pays for triples only: cherry 3× (1 in 20), bell 4× (1 in 25), spike 8× (1 in 50), diamond 20× (1 in 125), banana 40× (1 in 250) and Onkey 80× (1 in 500), a win about every 8 spins and a 95.00% return, each line paying back 15-16% (`chances()`, `rtp()`: the house edge is 5% on these lines alone), plus the secret Golden Onkey, 200× at 1 in 10,000, a bonus on top that `rtp()` leaves out unless `secret=True` (97% in all). A losing spin's reels are drawn by `draw_reel()` from the display weights `show` (the Golden Onkey 1 reel in 421, so it's rarely seen unless it hits) and redrawn if all three match; they only change what a loss looks like, never the odds. `SYMBOLS` order is stored in spins, so new symbols go at the end; `img` is drawn instead of the emoji (`glow` adds the Golden Onkey's golden filter) and `secret` (the Golden Onkey) keeps a symbol out of the pay table and off the reel strips. Retired `classic` results are still recoverable by request id, but new plays are rejected. Stakes are 5/10/25/50/100/250/500 virtual credits. Each spin updates the balance and inserts `slot_spins` in one locked transaction, with the machine's `rtp` (without the secret jackpot) at the time. `lines(name)` (a bettor's hits per symbol) and `house()` (every bettor's spins: the edge's expected take, stakes × (1 − rtp), the actual take, stakes − payouts, and `secret_paid`, the jackpots the edge doesn't cover; kept for later use) count only spins with `rtp`, so both start from when it was added, across seasons. `(bettor, request_id)` prevents duplicate payment. Reset tags rows with `season_id` (NULL is current) and preserves retry keys; `BetManager.reset` locks the standings snapshot with the reset. Leaderboard `slots` is season net, subtracted from match-betting profit; ROI and banana earnings exclude slots. `web/slots.js` (`FiveSlots`) renders one arcade-style cabinet, stake buttons, pay table (chance and your hits per line), and below it your recent spins, Your season (`season()`, from `me`'s `wins` / `best` / `since_win`) and the squad's Biggest wins this season (`bigWins()`, from `big_wins`; a win is a payout above the stake); wins on diamond, banana, Onkey and the Golden Onkey get celebrations that build on each other (`FX` / `celebrate()`, using app.js's `confetti()`). Its requestAnimationFrame loop translates repeating symbol strips (`stripsNow()`: built from the machine's display weights `show`, a cell per stop, spread evenly and laid out differently per reel, without secret symbols, which take over the landing cell (`swapped`) just before it rolls into view; motion is in cells, and `rest` keeps the cell each reel stopped on), accelerates and uses cubic Hermite deceleration to stop each reel on the first cell holding the server result after its natural run-out, with zero final velocity; leaving the tab cancels motion, and reduced motion skips rolling. When the first two reels match, the third may tease (`TEASE` chance by the pair's symbol, decided from the first two reels only so it shows on wins and losses alike; `TEASE_LEVEL` sets its length): it keeps spinning, pulses gold over a drone, creeps the last cells, teeters half on the pair's symbol to a heartbeat, then snaps a half cell onto its landing cell with an overshoot (brakes are lists of segments, each a function of progress), flashing gold with a sting or red with a sad trombone, and on a loss stops on a result cell next to the pair's symbol when the strip has one (a near miss; only the cell changes, never the result). Stops wait longer for bigger symbols (`PAUSE`, keyed to the reels already showing; a long opening spin on every banana, Onkey or Golden Onkey win and one spin in ten, `BIG_OPENING`; set as `dues` in `settle()`), and each reel clanks as symbols pass the line. The clank is one stream for the machine (at most every 70 ms across the reels). The cabinet has an LED frame round it (`LEDS`, `.slots-leds`: fixed lights with a chase running round them clockwise, two thirds lit, slow at rest, faster while spinning; a win flashes them all together, then each light rejoins the chase on its own turn; diamond and bigger wins mix in more colours (`--led`, by `.slots-tier-*`), up to a rainbow for the Golden Onkey; the content sits in `.slots-body`), a deck that's one control panel with recessed wells for the bet keys, readout and Spin button, a speaker toggle (`speaker()`), a chrome bezel with a glass glare, a pull lever (`lever()`, also spins), backlit bet keys, an amber readout (`readout()`) and a domed Spin button. Optional Web Audio tones have a persistent mute control. An uncertain request stays in sessionStorage per account and offers Check last spin after reload. Stakes lock while unresolved.
